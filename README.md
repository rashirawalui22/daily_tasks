# Course Project Portfolio REST API

A beginner-friendly Express and MongoDB API for publishing student course projects, browsing project details, and collecting visitor ratings and feedback.

## Technologies

- Node.js and Express.js
- MongoDB and Mongoose
- Jest, Supertest, and mongodb-memory-server for integration tests
- Postman collection for manual/API-runner testing

## Installation

1. Install Node.js 18 or newer and npm.
2. From the project root, install dependencies:

   ```bash
   npm install
   ```

3. Copy `.env.example` to `.env` and set your MongoDB connection string and port. The `.env` file is ignored by Git.
4. Start MongoDB locally, or create a MongoDB Atlas database and use its connection string in `MONGODB_URI`.
5. Start the API:

   ```bash
   npm start
   ```

   For development with automatic restarts:

   ```bash
   npm run dev
   ```

The API listens on `http://localhost:5000` by default. Change `PORT` in `.env` to use another port. The server connects to MongoDB before it starts listening.

### Environment variables

| Variable | Required | Example | Description |
| --- | --- | --- | --- |
| `PORT` | No | `5000` | HTTP port (defaults to 5000) |
| `MONGODB_URI` | Yes | `mongodb://127.0.0.1:27017/course_project_portfolio` | MongoDB connection URI |

Never commit `.env` or database credentials. `.env.example` contains placeholders only.

## Data models and relationship

- **Project** stores `title`, `description`, `technologies`, `githubUrl`, `liveUrl`, `owner`, `published`, and `createdAt`.
- **Feedback** stores a reference to its Project plus `name`, `email`, `rating`, `comment`, and `createdAt`.
- Feedback uses a separate collection and a required `project` ObjectId reference. Project detail responses include that project's feedback.
- New projects are published by default. The project creation endpoint does not accept a client-supplied `published` value.

## API endpoints

All endpoints are rooted at `/api/projects`. JSON responses use a `success` boolean and either `data` or a consistent `message` and `error` object. The API intentionally exposes exactly these four project/feedback endpoints.

### 1. Create a project

`POST /api/projects`

Required fields: `title`, `description`, `technologies` (a non-empty array of non-empty strings), `githubUrl`, and `owner`. `liveUrl` is optional and may be omitted or empty.

Example request:

```json
{
  "title": "Course Project Portfolio",
  "description": "A web app for students to showcase course projects.",
  "technologies": ["Node.js", "Express", "MongoDB", "React"],
  "githubUrl": "https://github.com/example/course-portfolio",
  "liveUrl": "https://portfolio.example.com",
  "owner": "Alex Student"
}
```

Success response (`201 Created`):

```json
{
  "success": true,
  "data": {
    "_id": "MongoDB-generated-id",
    "title": "Course Project Portfolio",
    "description": "A web app for students to showcase course projects.",
    "technologies": ["Node.js", "Express", "MongoDB", "React"],
    "githubUrl": "https://github.com/example/course-portfolio",
    "liveUrl": "https://portfolio.example.com",
    "owner": "Alex Student",
    "published": true,
    "createdAt": "2026-01-01T00:00:00.000Z",
    "__v": 0
  }
}
```

The ID and timestamp above illustrate the response shape; real values are generated by MongoDB.

### 2. Get all published projects

`GET /api/projects`

Returns an array of published projects, newest first. An empty database produces `200 OK` with `"data": []`.

Example response:

```json
{
  "success": true,
  "data": [
    {
      "_id": "MongoDB-generated-id",
      "title": "Course Project Portfolio",
      "description": "A web app for students to showcase course projects.",
      "technologies": ["Node.js", "Express", "MongoDB", "React"],
      "githubUrl": "https://github.com/example/course-portfolio",
      "liveUrl": "https://portfolio.example.com",
      "owner": "Alex Student",
      "published": true,
      "createdAt": "2026-01-01T00:00:00.000Z",
      "__v": 0
    }
  ]
}
```

### 3. Get project details

`GET /api/projects/:id`

Returns the project and its feedback. A malformed MongoDB ID or a valid ID that does not exist returns `404 Not Found`.

Example response:

```json
{
  "success": true,
  "data": {
    "_id": "MongoDB-generated-id",
    "title": "Course Project Portfolio",
    "description": "A web app for students to showcase course projects.",
    "technologies": ["Node.js", "Express", "MongoDB", "React"],
    "githubUrl": "https://github.com/example/course-portfolio",
    "liveUrl": "https://portfolio.example.com",
    "owner": "Alex Student",
    "published": true,
    "createdAt": "2026-01-01T00:00:00.000Z",
    "feedback": []
  }
}
```

### 4. Submit feedback

`POST /api/projects/:id/feedback`

All fields are required: visitor `name`, valid `email`, integer `rating` from 1 to 5, and non-empty `comment` up to 500 characters. The project must exist before feedback can be saved.

Example request:

```json
{
  "name": "Taylor Visitor",
  "email": "taylor@example.com",
  "rating": 5,
  "comment": "Clear presentation and a useful project."
}
```

Success response (`201 Created`):

```json
{
  "success": true,
  "data": {
    "_id": "MongoDB-generated-feedback-id",
    "project": "MongoDB-generated-project-id",
    "name": "Taylor Visitor",
    "email": "taylor@example.com",
    "rating": 5,
    "comment": "Clear presentation and a useful project.",
    "createdAt": "2026-01-01T00:00:00.000Z",
    "__v": 0
  }
}
```

### Status codes and errors

| Status | Meaning |
| --- | --- |
| `200` | Read succeeded |
| `201` | Project or feedback created |
| `400` | Missing/invalid fields, invalid URL/email/rating, or invalid JSON |
| `404` | Invalid/missing project ID or unknown route |
| `500` | Unexpected server error |

Validation errors return `success: false`, `message: "Validation failed"`, and `error: { "code": "VALIDATION_ERROR", "details": [...] }`. No record is written when validation fails.

Documented failure case—submitting feedback for a validly formatted ID with no matching project (`404`):

```json
{
  "success": false,
  "message": "Project not found",
  "error": {
    "code": "PROJECT_NOT_FOUND",
    "details": "No project exists with the supplied ID"
  }
}
```

Feedback is checked against the project before validation or insertion, so this request cannot create an orphan feedback record.

## Testing

Run the automated integration tests with:

```bash

```

The tests use an isolated in-memory MongoDB server; a running local MongoDB instance and `.env` are not needed. They exercise all four endpoints, empty-list behavior, malformed IDs, required fields, invalid URLs/emails/ratings/comments, and verify that failed feedback submissions do not increase the database record count. The in-memory MongoDB package may need to download its MongoDB binary the first time it runs.

### Postman

1. Start the API with `npm start`.
2. In Postman, choose **Import** and select `postman/collection.json`.
3. Run requests in collection order using the Collection Runner. The create request stores its real MongoDB-generated project ID for later requests. The missing-project request generates a fresh 24-character ID for its 404 case.
4. Check the response status and the collection test results for each request.

The automated integration tests, rather than a Postman collection run, are the verification for “no feedback was saved” because they assert the database record count directly.

## Day 3: Clinic appointment schemas and indexes

The clinic data layer adds Patient and Appointment Mongoose models and reusable services. It does not add clinic HTTP routes or store medical records; `reason` is limited to a short appointment booking reason. Patient email is normalized to lowercase and is not included in appointment query results.

### Patient schema

`src/models/Patient.js` stores a trimmed `fullName`, lowercase/trimmed unique `email`, required `phoneNumber`, optional `dateOfBirth`, and Mongoose-managed `createdAt`/`updatedAt` timestamps. Names and phone numbers have bounded lengths; email and phone values are validated, and dates of birth cannot be in the future.

### Appointment schema and relationship

`src/models/Appointment.js` stores `patientId` as a required ObjectId with `ref: 'Patient'`, plus required trimmed `doctorName`, future `appointmentDate`, short `reason`, enumerated `status`, and timestamps. Status defaults to `pending` and only accepts `pending`, `confirmed`, `cancelled`, or `completed`.

The relationship is one-to-many: each appointment stores one patient reference, and many appointments can refer to the same patient. Referencing is preferable to embedding because patients and appointments have independent lifecycles, and a patient may have an unbounded number of appointments; references avoid duplicating patient data in each appointment. The appointment model validates that its referenced patient exists, while `src/services/appointmentService.js` provides explicit ID/existence checks for service callers.

To retrieve one patient's appointments, the service filters by `patientId`, sorts by date, and populates only the patient's name:

```js
const { getPatientAppointments } = require('./src/services/appointmentService');

const appointments = await getPatientAppointments(patientId);
// Each appointment includes patientId: { _id, fullName }.
```

### Clinic indexes

Exactly two application-defined indexes are declared in the schemas (in addition to MongoDB's built-in `_id` index):

1. **Unique `{ email: 1 }` on Patient**: accelerates equality lookups by email during login or booking and enforces uniqueness under concurrent writes. The cost is extra disk/memory and index maintenance for patient inserts and email updates.
2. **`{ patientId: 1, appointmentDate: 1 }` on Appointment**: supports filtering appointments for one patient and sorting those appointments by date. This compound order matches the service query. It consumes storage and adds index maintenance to appointment inserts and updates.

### Clinic validation and safe errors

- Required fields, trimming, string lengths, email format, and phone format are enforced by the Patient schema.
- Duplicate patient email writes are translated by `createPatient` into a safe `409` error without echoing the submitted email. The shared Express error middleware also returns a generic `409` for duplicate-key errors.
- Appointment references must contain a valid ObjectId and point to an existing Patient. Invalid IDs and missing patients have safe `400`/`404` service errors.
- Appointment date must be in the future; status must match the allowed enum. Validation failures do not save documents.
- No extra medical history, diagnoses, or other sensitive clinical data is collected.

### Clinic usage example

The services support document creation without exposing a new HTTP endpoint:

```js
const { createPatient } = require('./src/services/patientService');
const { createAppointment } = require('./src/services/appointmentService');

const patient = await createPatient({
  fullName: 'Morgan Patient',
  email: 'morgan@example.com',
  phoneNumber: '+1 (415) 555-0132'
});

const appointment = await createAppointment({
  patientId: patient._id,
  doctorName: 'Dr. Rivera',
  appointmentDate: new Date(Date.now() + 24 * 60 * 60 * 1000),
  reason: 'Annual checkup'
});
```

### Clinic assumptions

- Appointment dates represent future bookings; past appointments cannot be newly created through this model.
- Phone validation accepts common international punctuation and requires at least seven digits.
- Email checks validate a practical address format and uniqueness, not mailbox ownership.
- Clinic schemas and services are independent of the existing portfolio API; no clinic routes were requested.
